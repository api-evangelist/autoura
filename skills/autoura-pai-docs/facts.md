## Facts

Each current provenance Fact is stored as one record and belongs to one Visit or Stop through `content_id`.

A provenance Fact is one distinct, useful, source-supported visitor-planning claim or decision detail about its owning Visit or Stop, recorded as one current Fact against the most appropriate `content_field`. It is separate from a Visit's six preview facts.

Record independent claims as separate Facts, even when they appear in one sentence, and record the same claim only once when repeated across fields. Facts may cover tickets, timings, access, facilities, restrictions, dining, seasonal conditions, events, and named related places.

Do not count duplicated or reworded claims, URLs or source metadata, internal notes, empty fields, generic marketing, unsupported opinion, or curator recommendations and tips unless their underlying factual claim is separately sourced.

Example:

```json
{
  "fact_id": "fact-example",
  "content_id": "visit-example",
  "content_field": "practical",
  "fact": "The main entrance has step-free access.",
  "source": "https://example.com/accessibility",
  "last_verified_UTC": "2026-07-30 17:30:00",
  "who_verified": "Autoura content team",
  "status": "confirmed",
  "note": "Verified against the venue's official accessibility page."
}
```

Fields:

| Field | Meaning |
|---|---|
| `fact_id` | Stable identifier generated by Autoura when the Fact is created |
| `content_id` | Owning Visit ID or Stop ID |
| `content_field` | Factual top-level field on the owning Visit or Stop, such as `location`, `ticketing`, `accessibility`, or `shop` |
| `fact` | The visitor-facing fact that was checked |
| `source` | Public web link used to verify the fact. Must start with `http://` or `https://` |
| `last_verified_UTC` | Full UTC datetime when Autoura last verified the Fact, set by the server |
| `who_verified` | Person, team, organisation, or process that verified the fact |
| `status` | `confirmed`, `needs_review`, or `disputed` |
| `note` | Optional public-display-safe verification context |

Status meanings:

- `confirmed`: a current, source-backed Fact
- `needs_review`: still a Fact, but its freshness or evidence requires reassessment without a specific contradiction
- `disputed`: a concrete challenge or conflicting evidence exists

Use `visits_search` with `has_provenance_exceptions: true` to find Visits that own at least one current `needs_review` or `disputed` Fact. This filter does not imply a Visit workflow; combine it with `workflow: "published"` for the weekly published-Visit provenance review.

Create requires `content_id`, `content_field`, `fact`, `source`, `who_verified`, and `status`. `note` is optional.

`last_verified_UTC` and `date_created_UTC` are set to the current server UTC time when a Fact is created or replaced. Callers must not supply either timestamp.

`content_field` must be one of the factual top-level fields supported by the PAI update tool for the owning content type. Visit and Stop fields are validated separately. Workflow, refresh configuration, content-gap calculation fields, curator-only presentation fields, and other maintenance metadata are not factual fields.

Visit factual fields:

`visit_theme`, `annual_visitors`, `annual_visitors_source`, `name`, `website_url`, `video_url`, `nibble`, `summary`, `description`, `background`, `who_for`, `comingup`, `location`, `timezone`, `getting_there`, `dining`, `practical`, `planning`, `ticketing`, `when`.

Stop factual fields:

`stop_type`, `stop_class`, `date_type`, `timezone`, `weather`, `name`, `website_url`, `video_url`, `nibble`, `summary`, `important`, `description`, `background`, `location`, `group`, `pets`, `accessibility`, `gambling`, `lgbtq`, `activity`. `shop` is supported for non-accommodation Stops. `food` is supported only for Food & Drink Stops.

Use `facts_create` to create one or more Facts. The complete input array is validated before any Facts are saved.

Changed Facts must receive a new Fact ID. Prefer `fact_delete` followed by `facts_create`. `fact_update` implements the same replacement rule by deleting the old Fact and returning a newly created Fact with a new Fact ID.

Use `fact_verify` to verify an unchanged Fact. It retains the existing Fact ID and content and sets `last_verified_UTC` to the current server UTC time.

As with `facts_create`, `fact_verify` requires the caller to supply `who_verified`, for example `sahra-configurer-3`. That identity is saved on the existing Fact. The caller cannot provide a verification timestamp.

When changing factual content with `visit_update` or `stop_update`, supply `fact_references`. Every factual top-level field changed in that request must have at least one reference whose `content_field` matches the changed field. The referenced Fact must exist and belong to the same Visit or Stop.

For the top-level `summary` field, the referenced Fact's `fact` text must also match the submitted summary after case, repeated whitespace, and a final period are normalised. This is an exact deterministic check, not semantic AI validation. Other factual fields continue to use ownership and `content_field` validation only because their structured or composite values may legitimately be supported by smaller distinct Facts.

Example:

```json
{
  "fact_references": [
    {
      "content_field": "practical",
      "fact_id": "fact-example"
    }
  ]
}
```

Multiple Facts may support the same changed field by adding more rows. References to unchanged fields, unknown Fact IDs, Facts owned by different content, Facts bound to another field, and duplicate Fact IDs are rejected before the Visit or Stop update.

Unknown fields are rejected.

Use `note` only when it adds useful verification context. Omit it when there is nothing useful to add.
